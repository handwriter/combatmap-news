# Удалённый баланс Combat Map

Редактор: Sveltia CMS → **Баланс игры**. Предпросмотр после публикации:
`https://handwriter.github.io/combatmap-news/balance.html`.
Для первого подключения нужен клиент с `IBalanceService` из репозитория CombatMap.

## Изменение баланса

1. Открыть **Тестовый баланс**. Базовый юнит задаёт значения пехоты и наследуемых полей шести вариантов.
2. В **Переопределениях юнитов** заполнить только отличающиеся или намеренно независимые поля.
   Пустое число / «Наследовать» означает наследование. Число `0`, «Нет» и значение, равное базовому,
   являются явными переопределениями. Минимум и максимум интервала редактируются отдельно.
3. Настроить общие механики, города, существующие исследования и ИИ. Описание и допустимый диапазон
   находятся под каждым полем. Значение нуля зависит от параметра; положительные минимумы запрещают ноль.
4. Предпросмотр черновика показывает эффективные значения, источник и отличия от опубликованного prod.
   Сохранить. Дождаться успешного **Publish game content**, затем открыть опубликованный предпросмотр.

Очистка общего переопределения возвращает значение базы. Поля компонента, которого нет у базы,
обязательны для соответствующего типа: наследовать для них нечего. Настройка не добавляет компоненты.
Параметры карты, графика, звук, технические сетевые лимиты и диагностика остаются в игре / карте.

## Публикация в prod и откат

1. Проверить test в клиенте из любой Steam-ветки, кроме default/public.
2. На странице предпросмотра выбрать проверенную ревизию. Скопировать **полный коммит** и **SHA-256**.
3. Открыть **Публикация в продакшн / откат**, вставить оба значения и написать комментарий. Сохранить.
4. Дождаться успешной публикации. В prod окажется весь баланс выбранного коммита: база, переопределения,
   города и общие конфиги. Последующие правки test его не меняют.

Откат: выбрать прежнюю ревизию и повторить эти действия. Исторические снимки продолжают публиковаться
по адресам с хэшем. Неверный хэш, неизвестный коммит, несовместимая схема или ошибка значений отменяют
сборку; Pages сохраняет предыдущую успешную публикацию.

Пустой коммит означает первоначальный **prod-bootstrap.json**, а не текущий test. Этот файл после первого
релиза следует сохранять неизменным. Ожидаемый хэш обязателен и для него. В локальной сборке с незакоммиченными
правками предпросмотр показывает HEAD; использовать такую ревизию для продвижения нельзя. Продвигать следует
ревизию успешно опубликованного сайта.

## Файлы и сборка

| Файл | Назначение |
|---|---|
| `content/balance/test.json` | Единая редактируемая модель; одно сохранение — целостная ревизия |
| `content/balance/promotion.json` | Точный коммит test, ожидаемый хэш и комментарий prod |
| `content/balance/prod-bootstrap.json` | Замороженная первоначальная модель prod |
| `content/balance/exported-baseline.json` | Последний экспорт из Unity; не заменяет правки test |
| `schema/balance-catalog.json` | Поля, типы, ограничения, описания и доступные компоненты типов |
| `schema/balance-definition.schema.json` | Контракт нормализованной модели с разреженными переопределениями |
| `schema/balance-snapshot.schema.json` | Контракт полностью рассчитанного снимка |
| `schema/balance-manifest.schema.json` | Контракт манифеста канала |
| `scripts/balance.mjs` | Разрешение наследования, точное продвижение, история и публикация |
| `site/balance-model.js` | Общая валидация и наследование для сборщика и предпросмотра CMS |

Сборка требует Node 20+ и полной Git-истории. GitHub Actions получает её через `fetch-depth: 0`.

```sh
npm ci
npm run balance:editor   # после обновления каталога Unity; сохраняет существующий контент
npm run build
```

Выход: `dist/v1/balance/test.json`, `prod.json` и `snapshots/<sha256>.json`.
Манифест содержит версию схемы, канал, исходный Git-коммит, SHA-256, размер в байтах и относительный URL.
Хэш считается по точным UTF-8 байтам JSON со стабильным порядком ключей, без завершающего перевода строки.
Клиент проверяет эти байты, а не сериализует снимок повторно. Предпросмотр и список ревизий опубликованы
в `preview.json` и `revisions.json`; игра их не загружает.

Пустые переопределения удаляются при сохранении CMS и нормализуются сборщиком. Вычисленные базовые значения
никогда не записываются в переопределения. Валидатор проверяет точный набор полей, типы, диапазоны, ссылки,
интервалы, соответствие морской формы среде передвижения и отсутствие циклов исследований.

## Экспорт из Unity и развитие схемы

В Unity открыть **CombatMap → Balance → Export baseline and authoring catalog**. Экспортёр использует
модификации префаба, сопоставляет компонент и сериализованное поле, учитывает изменения масштаба коллайдеров
и сохраняет явно заданные значения, даже равные базе. Стоимость и доступность производства каждого варианта
записываются явно. Геометрические размеры коллайдеров экспортируются в мировых единицах.

Результат в клиенте: `Assets/Resources/Balance/catalog.json` и `baseline.json`.
По умолчанию контент ищется в соседнем `combatmap-news`; иной путь задаётся переменной `COMBATMAP_CONTENT_ROOT`
при запуске Unity. Затем выполнить `npm run balance:editor` и сохранить изменения обоих репозиториев.
Экспорт не перезаписывает существующий test или первоначальный prod.

Новые поля, типы, компоненты и несовместимые изменения требуют согласованного обновления схемы, встроенного
снимка, клиента и сетевого протокола. Изменение состава каталога само по себе не обновляет действующие модели.
При миграции разработчик явно переносит test и prod в новую схему; содержимое старых схем нельзя продвигать
как совместимое без такой миграции.

## Ручная приёмка

1. Сравнить первоначальные характеристики всех семи типов, города и столицы с текущим клиентом.
2. Изменить базовое HP: наследующие типы меняются, явные переопределения сохраняются. Очистить одно
   переопределение; затем проверить явное значение, равное базе, после следующей правки базы.
3. Проверить `0`, «Нет», независимые границы прицеливания и перезарядки, геометрию и производство.
4. Опубликовать test, продвинуть выбранную ревизию, снова изменить test и откатить prod. Проверить,
   что prod остаётся точным снимком выбранного коммита.
5. Создать сетевое лобби с разными локальными кэшами. Проверить ожидание готовности, зрителя,
   переподключение, смену хоста и одинаковый хэш комнаты у участников.
6. Опубликовать новые параметры во время матча: матч и быстрый рестарт сохраняют прежний снимок.
   Вернуться всем в лобби после истечения интервала запроса; следующий бой получает новый снимок
   после повторного подтверждения готовности.
7. Записать и открыть новый реплей после изменения сайта. Проверить старый реплей без снимка.
8. Проверить недоступный сайт, повреждённый кэш и ошибочный ответ: сначала корректный кэш нужного
   канала / схемы, затем встроенный снимок. Ошибочный снимок комнаты блокирует старт, пока не получен корректный.

Play Mode и сетевую приёмку выполняет пользователь. Автоматические тесты для этой задачи не добавлялись
и не запускались согласно `CombatMap/AGENTS.md`.
